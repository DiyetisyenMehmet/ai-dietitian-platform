# Diewish Staging Preview

This environment exists only to test current `fix/production-hardening` builds on real Android devices without pointing debug APKs at production services or production data.

## Isolation guarantees

- Google Cloud project: `project-a2e260c1-839d-4f1d-b90`
- Region: `europe-west1`
- Cloud Run backend: `diewish-backend-staging`
- Cloud Run frontend: `diewish-frontend-staging`
- Artifact Registry: `diewish-staging`
- Runtime identity: `diewish-staging-runtime@project-a2e260c1-839d-4f1d-b90.iam.gserviceaccount.com`
- Deploy identity: `diewish-staging-deployer@project-a2e260c1-839d-4f1d-b90.iam.gserviceaccount.com`
- Database: separate Neon project `Diewish Staging` (`shiny-hill-56015697`)
- Database name: `diewish_staging`
- No production database branch/copy is used.
- Debug APKs require an explicit staging web URL and do not silently default to production.
- Production deployment is not part of the staging workflow or bootstrap.

## Why staging has a separate database

Diewish can contain health and nutrition data. A Neon branch of the production project would copy production data into staging. Scanner testing does not need those rows, so staging uses a clean independent project.

## One-time Google Cloud bootstrap

The repository includes `scripts/bootstrap-staging-gcp.sh`. Run it from Google Cloud Shell while authenticated to the Diewish Google Cloud project.

The script is idempotent and performs the staging-only bootstrap:

1. Enables Cloud Run, Cloud Build, Artifact Registry, Secret Manager, Vertex AI, IAM Credentials and STS APIs.
2. Creates the `diewish-staging` Docker repository when missing.
3. Creates `diewish-staging-runtime` and `diewish-staging-deployer` service accounts when missing.
4. Grants Vertex inference access to the runtime identity.
5. Creates/rotates the staging secrets listed below.
6. Configures GitHub OIDC Workload Identity Federation restricted to `DiyetisyenMehmet/ai-dietitian-platform` and the `feature/staging-preview` ref.
7. Grants the deployment identity build/deploy permissions and permission to act as the staging runtime identity.
8. Grants the runtime identity access only to the runtime staging secret payloads.
9. Grants the Cloud Build identity access only to the direct migration database secret and staging Artifact Registry writer access.

The script does not deploy or update the production Cloud Run services.

## Secret Manager contract

Staging uses:

- `diewish-staging-database-url` — pooled/runtime Neon connection
- `diewish-staging-direct-database-url` — direct Neon connection used only by Prisma migration in Cloud Build
- `diewish-staging-jwt-access`
- `diewish-staging-jwt-refresh`

JWT values are generated by the bootstrap script. The database secrets target the clean Neon project `shiny-hill-56015697`. Keep database connection strings out of GitHub, source files and chat messages.

USDA production credentials are deliberately not copied into staging. Scanner preview uses USDA FoodData Central's public low-limit `DEMO_KEY` for test traffic. It is not used by production.

## GitHub OIDC

No long-lived Google JSON key is stored in GitHub. The workflow uses the deterministic OIDC resources created by the bootstrap script:

- Provider: `projects/730419163638/locations/global/workloadIdentityPools/github-actions/providers/diewish-staging`
- Service account: `diewish-staging-deployer@project-a2e260c1-839d-4f1d-b90.iam.gserviceaccount.com`

No GitHub repository/environment secret or variable is required for Google authentication after bootstrap.

## Controlled deployment trigger

`.github/workflows/staging-preview.yml` listens to `feature/staging-preview`, but its deploy job is skipped for ordinary pushes.

A deployment runs only when either:

- the workflow is manually dispatched where GitHub permits it, or
- the HEAD commit message contains the literal marker `[deploy-staging]`.

Never use `[deploy-staging]` in ordinary development commits.

## Same-origin API contract

Cloud Run gives the frontend and backend separate `run.app` hosts. The staging browser and Android WebView do not call the backend host directly. Instead:

1. `NEXT_PUBLIC_API_BASE_URL` is `/api`.
2. The Next.js server rewrites `/api/:path*` to the isolated staging backend using the server-only `DIEWISH_API_PROXY_TARGET` build value.
3. The browser therefore sees the refresh cookie as first-party on the frontend origin.
4. `REFRESH_COOKIE_SAME_SITE=lax` remains enabled.
5. Android WebView continues to reject third-party cookies.

This avoids weakening the release auth model merely to accommodate Cloud Run's separate service hostnames.

## Deployment sequence

The workflow performs:

1. OIDC authentication to Google Cloud.
2. Staging resource preflight checks.
3. Prisma migration against the clean staging database through the direct Neon endpoint inside Cloud Build.
4. Exact-SHA backend image build and publication.
5. Deployment of `diewish-backend-staging` with the staging runtime identity and pooled/runtime database URL.
6. Backend URL discovery.
7. Exact-SHA frontend build with browser API base `/api` and the staging backend as the private rewrite target.
8. Deployment of `diewish-frontend-staging`.
9. Backend CORS and `APP_WEB_URL` binding to the resolved staging frontend.
10. Direct backend health, frontend page health and same-origin `/api/health` proxy verification.
11. Android debug APK build with `DIEWISH_WEB_BASE_URL` set to the resolved staging frontend URL.
12. Upload of the APK, SHA-256 and exact-SHA staging manifest.

## AI and nutrition providers

Staging uses:

- `AI_PROVIDER=vertex`
- `VERTEX_AI_LOCATION=global`
- `VERTEX_AI_MODEL=gemini-3.5-flash`
- Cloud Run service identity for Vertex authentication
- USDA FoodData Central `DEMO_KEY` with intentionally low test limits
- Open Food Facts without a provider secret

No AI credential is embedded in the frontend or Android APK.

## Promotion rule

A successful staging test does not deploy production. Production promotion remains a separate explicit operation after:

- exact-SHA Hardening CI is green,
- Staging Config CI is green,
- staging direct and same-origin health checks pass,
- real Android CameraX photo capture passes,
- real ML Kit barcode scanning passes,
- Vertex/Gemini food recognition succeeds for food and non-food images,
- USDA/Open Food Facts lookup and deterministic nutrient calculation are verified,
- safe-area behavior is checked on the target Android device.

## Deployment probes

The deploy marker commit is documentation-only and exists solely to trigger the isolated staging workflow after exact-SHA CI has passed.
