## Causal chain and ruled-out explanations

The frontend submits only email/password to AUTH_ENDPOINTS.login=/auth/login,
relative to its API base; the expected full route is /api/auth/login. The server
registers that exact route, validates the payload and then looks up the user in
Postgres before checking the password or issuing a session. HTTP 422 proves
requests reach validation. The valid-shaped unknown account also gets HTTP 500,
so the failure does not depend on the user's password correctness, usable-password
marker, account recovery identity or successful cookie/session issuance.

The currently served login page's public compiled assets were also checked:
`1326-8bb629b3181e14d6.js` contains the /auth/login endpoint and apiBaseUrl=/api;
`app/layout-de3ae526a3eeca4c.js` contains apiBaseUrl=/api. The login-page asset
contains the same generic Turkish 5xx message. Entire bundle contents were not
printed or saved in evidence. This confirms the observed endpoint/base in the
served client as well as in repository source.

The same-origin proxy reaches the backend: both liveness and readiness show the
backend JSON contract, and the direct backend has the same failed dependency.
Neon's rejected SELECT 1 independently identifies the dependency failure as quota
access denial. This is a backend/environment failure surfaced by the frontend,
not an invented frontend 5xx or a country-picker/browser-test fixture issue.

The exact Turkish message is intentionally generated by the existing
application/auth/auth-service.ts for ApiError.status >= 500. Network failures,
401, 422 and 429 have different messages. No credentials, CSRF, origin, feature
flag or reCAPTCHA control is bypassed to make login appear successful.

The latest successful standard staging deployment in Actions was run
[39032420125](https://github.com/DiyetisyenMehmet/ai-dietitian-platform/actions/runs/39032420125),
source `12c15074c71c6bc3c84fc7a32b02eaa71f4f32c7`, previously verified backend
revision `diewish-backend-staging-00478-2fq` and frontend
`diewish-frontend-staging-00239-gm2`. Newer repository source is not proof of a
new serving revision. Current Cloud Run revision/image configuration could not
be independently re-read from this session (no authenticated Cloud Run reader).
No staging-ref OIDC restriction was bypassed or deployment triggered. That
version-verification limit does not change the direct provider quota evidence.

## Targeted verification

New `frontend/tests/email-login-response-contract.test.cjs` executes the existing
service -> auth client -> HTTP client chain with synthetic transport. Eight
cases check the real endpoint, JSON-only email/password payload, included cookie
policy, no unexpected retry/provider request, success envelope, 500/503 generic
message, distinct 401/422/429 responses, transport failure and missing API config.
The test does not encode live 500 as healthy behavior or claim successful live
login. A dedicated PR workflow runs only these tests; accepted auth/recovery/
reCAPTCHA and unrelated suites are not rerun. Local result: **8/8 passed**.
No product code correction is justified by the observed incident.
